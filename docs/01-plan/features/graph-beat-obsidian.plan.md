## 2. 실측 데이터 (설계 근거)

모든 수치는 볼트 사본(`A:/claude-temp/.../index.db`, F: 원본 불가침)에 대해 측정.

### 2.1 볼트 규모
- 문서 **17,303개** (메모리에 기록돼 있던 12,850은 낡은 값)
- `getDocumentsMeta()` 전량 1,752 ms
- `getDocumentEmbeddingsByIds()` 17,303개 **4,688 ms** — 선형, 문제 아님

### 2.2 엣지 생성 — 현재 방식 vs 제안

| n | 현재 (페어 객체 전량 적재) | 제안 (노드당 top-K 고정 배열) |
|---|---|---|
| 3,000 | 2,695 ms / 3.18M pairs / **234 MB** | 2,208 ms / 15K / **16 MB** |
| 6,000 | 11,698 ms / 13.1M pairs / **937 MB** | 9,018 ms / 30K / **29 MB** |
| 17,303 (외삽) | ~97 s / ~109M pairs / **~7.8 GB → OOM** | ~75 s / 86K / **~84 MB** |

**결론**: `GRAPH_NODE_CAP=3000`은 성능 튜닝이 아니라 **OOM 회피 방벽**이었다. 메모리를 선형으로 만들지 않으면 캡을 못 푼다.

### 2.2.1 T1.1 구현 후 실측 (완료)

`buildGraphData(nodeCap: 20000)` 를 실볼트 사본에 대해 종단 실행:

```
전량 빌드: 101,527 ms
  nodes 17,302   edges 70,398   clusters 10
  heapUsed 93 MB   rss 205 MB   heapTotal 110 MB
```

- **OOM 해소 확인** — 외삽 7.8 GB → 실측 **93 MB**
- 엣지 집합 동일성: 옛 알고리즘과 대조해 n=999 / n=2,999 에서 **완전 일치**(onlyOld 0, onlyNew 0) → 순수 메모리 수정임이 실증됨
- 남은 문제는 **시간(101.5초)** → T1.2

### 2.2.2 임계값 관찰

무작위 페어 200k 표본에서 `edgeThreshold=0.35` 통과율이 **37.8%**. 임계는 절반 조금 넘게만 걸러내고, 실제 엣지 선택은 전적으로 top-K가 한다. 임계를 필터로 신뢰하지 말 것(후속 튜닝 대상).

### 2.3 기각된 대안 — `findDocumentNeighbors`

스토어에 `findDocumentNeighbors(embedding, limit)`가 이미 있고 주석은 *"sqlite-vec KNN(HNSW), O(K log n)"* 이라고 주장한다. **프로덕션 호출자는 0개**(테스트 스텁만).

실측: **문서당 220 ms** → 17,303개면 **약 63분**. 현재 JS 방식보다 100배 느리다.
원인: sqlite-vec의 `MATCH ... k=?`는 HNSW가 아니라 **전수 스캔**이고, 문서당 1쿼리라 오버헤드가 지배한다.

→ 채택하지 않는다. 주석이 사실과 다르므로 **정정하거나 제거**한다 (T1.4).

## 3. 트랙 T1 — 전량 스케일 (3,000 → 17,303)

의존 관계상 **가장 먼저**. T2/T3가 다루는 노드 집합의 크기를 여기서 확정하기 때문.

### T1.1 페어 배열 제거 → 노드당 top-K 고정 (**하드 블로커**)
`buildGraphData`의 `neighbors: Array<Array<{peer,sim}>>` 를 `Float32Array(N*K)` + `Int32Array(N*K)` 고정 슬롯으로 교체.
임계 통과 페어를 전부 적재하지 않고, 그 자리에서 노드별 top-K 슬롯에 offer 한다.
- 메모리 O(pairs) → O(n·k)
- 부수 효과: 거대 배열 정렬이 사라져 시간도 ~20% 감소 (실측)
- 동작 동일성: 최종 엣지는 "노드당 상위 K개 이웃"으로 **현재와 같은 정의**. 동점 처리 순서만 달라질 수 있음 → 테스트로 고정

### T1.2 병렬 정확 계산 + 이벤트루프 오프로드 ✅ 설계 확정
T1.1 이후 전량 빌드는 **101.5초**(실측). 단일 스레드 Express 핸들러가 그동안 완전히 멈춘다.

`node:worker_threads` W개로 **i-루프를 행 구간별로 분할**하고 `SharedArrayBuffer`로 `flat`을 공유한다.
각 워커는 자기 구간의 top-K 슬롯만 채우고, 메인이 병합한다.
- 결과는 **정확**하다 — 근사·품질 손실 0
- 이 머신 16 논리 코어(8 물리) → 8워커면 101초 → **~13초** 기대
- 메인 스레드는 놀고 있으므로 **T1.2가 이벤트루프 오프로드를 겸한다**
- 첫 요청은 "빌드 중"을 즉시 반환하고 진행률 폴링 (`/api/graph/status`)
- 캐시(5분 TTL) 유지 — 워커 결과를 채운다
- 워커당 top-K 슬롯은 `Float32Array`/`Int32Array` → 병합은 단순 offer 재적용

### ~~T1.3 클러스터 블로킹~~ — **기각 (측정 근거)**

"먼저 k-means로 묶고 클러스터 내부 + 인접 M개만 비교" 안을 실측했다.

| 인접 M | top-5 recall | 노드당 후보 | 전량 대비 |
|---|---|---|---|
| 0 (내부만) | **46.5%** | 274 | 1.6% |
| 1 | 54.6% | 592 | 3.4% |
| 3 | 63.6% | 1,152 | 6.7% |
| 6 | **72.0%** | 1,943 | 11.2% |

k-means 자체는 싸다(k=80·3회 = 2.8초). **문제는 정확도다.** 가장 넓게 잡아도 정답 top-5의 28%를 놓치고, 그때는 후보가 이미 전량의 11%라 속도 이득도 ~9배뿐이다.

이 뷰의 주장은 "이게 네 지식의 가장 강한 연결"이다. 그 연결의 1/4을 조용히 틀리게 만드는 근사는 **성능과 바꿀 수 없다.** 고차원 임베딩에서 유클리드 k-means 경계가 최근접 이웃을 잘 보존하지 못하는 게 원인이며, 파라미터로 메울 수 있는 종류가 아니다.

→ 정확한 병렬화(T1.2)로 간다. 그래도 부족하면 다음 후보는 **랜덤 프로젝션 2단계**(384→96 차원으로 후보 생성 후 정확 재채점) — JL 보조정리상 거리 보존이 k-means 블로킹보다 훨씬 낫고, 재채점이 정확도를 복구한다. 채택 전 같은 방식으로 recall 측정할 것.

### T1.4 죽은 코드 처리
`findDocumentNeighbors` — 삭제하거나, 남긴다면 주석에 **실측치(220 ms/doc, sqlite-vec는 HNSW 아님 = 전수 스캔)** 를 박아 다음 사람이 같은 함정에 빠지지 않게 한다.

## 4. 트랙 T2 — 링크 그래프 (해자의 핵심)

### T2.1 스키마: `links` 테이블
```sql
CREATE TABLE IF NOT EXISTS links (
  source_doc TEXT NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
  target_path TEXT NOT NULL,   -- 해석 전 원문 타깃 (링크가 깨져도 보존)
  target_doc  TEXT,            -- 해석된 문서 id (미해결이면 NULL = 끊어진 링크)
  anchor      TEXT,            -- #heading / ^block
  alias       TEXT,            -- [[target|alias]] 의 alias
  kind        TEXT NOT NULL    -- 'wikilink' | 'markdown' | 'embed'
);
```
- 인덱스: `(source_doc)`, `(target_doc)`, `(target_path)`
- `createTables()`의 기존 `CREATE TABLE IF NOT EXISTS` 패턴을 그대로 따름 → 기존 DB에 **비파괴 추가**

### T2.2 인덱서 추출
`scanner.ts`가 이미 본문을 읽는 지점에서 링크를 뽑는다(추가 I/O 0).
- `[[target]]`, `[[target|alias]]`, `[[target#heading]]`, `[[target^block]]`, `![[embed]]`
- 표준 마크다운 `[text](path.md)` 중 볼트 내부 상대경로
- 코드블록/인라인코드 안의 `[[...]]`는 제외
- 타깃 해석: 파일명 → 경로 → 대소문자 무시 순. 실패해도 행은 남긴다(끊어진 링크 = 유용한 신호)
- **볼트는 읽기 전용** — 추출은 절대 파일을 쓰지 않는다

### T2.3 그래프 엣지 2종
`GraphEdge`에 `kind: 'link' | 'semantic'` 추가(기본 `'semantic'`으로 하위호환).
- 링크 엣지: 실선 + 밝게 + 방향성 표시
- 시맨틱 엣지: 기존 흐린 선
- 같은 페어에 둘 다 있으면 링크가 이긴다(가장 강한 신호)
- 토글: 링크만 / 의미만 / 둘 다 — 옵시디언 유저가 "내 링크만" 볼 수 있어야 함
- 클러스터 뷰의 메타엣지도 두 종류를 각각 집계

### T2.4 로컬 그래프 (현재 노트 N-hop)
- 웹: 노드 선택 → "이 노트 중심으로 보기" → BFS N-hop(기본 2, 슬라이더 1~3)
- 데스크탑: 노트 열면 우패널에 자동
- 링크 엣지 우선 확장, 의미 엣지는 옵션
- 기존 `bfsVisitOrder`(graph-core) 재사용

## 5. 트랙 T3 — 폴더 계층 + 태그 노드

### T3.1 폴더 계층 드릴다운
현재: 은하 → 행성 → 멤버 노트(평면). 서브폴더 정보는 `split('/')[0]`에서 버려진다.
- 서버 `members` 페이로드에 각 노트의 **다음 경로 세그먼트**를 실어 보낸다
- folder 모드 드릴인 시 서브폴더가 있으면 다시 접어서 보여주고, 없으면 노트로 펼친다
- 클라에 드릴다운 **스택** 도입(현재는 단일 `focusedClusterId`) → 브레드크럼 `볼트 / 04_Projects / stellavault`
- 뒤로가기가 한 단계씩 올라가야 함(현재는 무조건 은하로 복귀)

### T3.2 태그 노드
- `documents.tags`(이미 인덱싱됨)를 노드로 승격, 노트→태그 엣지
- 토글로 on/off (기본 off — 기존 화면을 바꾸지 않음)
- 태그 노드는 시각적으로 구분(다른 모양/색)

## 7. 리스크와 완화

| 리스크 | 심각도 | 완화 |
|--------|--------|------|
| 전량 O(n²) 메모리 OOM | **High (실측 확인)** | T1.1 top-K 고정을 **최우선**으로. 이것 없이는 캡을 풀지 않는다 |
| 마이그레이션이 기존 인덱스 손상 | High | `CREATE TABLE IF NOT EXISTS`만 사용, 기존 테이블 ALTER 없음. 사본으로 먼저 리허설 |
| 링크 추출이 볼트에 쓰기 | **Critical** | 추출 경로는 읽기 전용 함수만. SC8로 해시 대조 |
| 엣지 2종이 검색/RRF 회귀 유발 | Medium | `kind`는 그래프 전용 필드, 검색 경로는 손대지 않음. 기존 테스트로 확인 |
| 전량 렌더가 프론트에서 프레임 드랍 | Medium | 렌더는 이미 THREE.Points(인스턴싱) — 17k는 감당 범위. 실측 후 필요 시 LOD |
| T1.3 클러스터 블로킹이 엣지 품질 저하 | Low | 선택 사항. 채택 전 전량 대비 엣지 일치율 측정 |

## 8. 실행 순서

```
T1.1 top-K 고정 (OOM 해제)        ✅ 완료 — 7.8GB→93MB, 엣지 집합 동일성 실증
  └ T1.2 병렬 정확 계산 + 오프로드  ← 다음. 캡 해제의 전제 (101s → ~13s 목표)
      └ T1.4 죽은 코드 정리
      └ ~~T1.3 클러스터 블로킹~~    ✗ 기각 (recall 72% — §3 참조)
T2.1 links 스키마
  └ T2.2 인덱서 추출
      └ T2.3 엣지 2종 + 토글
          └ T2.4 로컬 그래프
T3.1 폴더 계층 드릴다운            ← T1/T2와 독립, 병행 가능
T3.2 태그 노드
```

**캡 해제 정책**: T1.2 완료 전까지 `GRAPH_NODE_CAP` 기본값은 그대로 둔다. 101초 블로킹을 기본 경험으로 만들 수 없다. T1.2 후 기본값 상향 + 전량 모드를 UI 토글로 노출한다.
